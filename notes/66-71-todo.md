What each actually is

#66 (enhancement) is the foundation: add a privy_id/privy_did column to employee + employer, capture the DID (already sitting in req.user.sub) at registration / on login, add by-privy-id lookups, and simplify the frontend fallback chain in App.jsx. On its own it's labeled low-urgency hardening.

#71 (security) is the payoff, and it explicitly says "Depends on #66." Right now the client-controlled x-wallet-address header is the authorization source in 13 spots across 6 controllers plus the requireApprovedEmployer middleware. A valid JWT holder can send someone else's address and be treated as them. The fix is to authorize off req.user.sub → DB record by DID, demoting the header to display metadata.

So the dependency direction is fixed: you can't do #71 without #66's column and the DID being populated on records.

Recommended sequencing

Don't treat these as two monolithic tickets in series. #66 as written bundles a security prerequisite (the column + fill-on-login) with lower-value cleanup (the frontend lookup rewrite). Split along that seam and put the security work adjacent:

1. #66a — the shared foundation (backend only). Migration 032 adding the DID column (nullable, UNIQUE, indexed) to both tables + "fill on login" capture in verifyToken / registration. This is the minimum #71 needs. Small, isolated, low-risk.
2. #71 — flip authorization. Set req.privyDid = verified.sub, then convert the 6 controllers + requireApprovedEmployer to look up the record by DID instead of trusting the header. This is where the actual security value lands, and it's the bulk of the total effort.
3. #66b — the cleanup. by-privy-id endpoints + rewriting the App.jsx email→wallet→phone fallback. Nice-to-have, no security stakes, safe to do last or defer.

Rationale: doing #66a→#71 back-to-back means the DID plumbing is fresh in context when you rewire authz, and you get the security fix without waiting on the frontend refactor. Step 3 is genuinely independent and shouldn't block the security work.

Two things to decide before you start

- Column name: #66 says privy_id, #71 says privy_did. Pick one now (I'd use privy_did — it's what the JWT claim is, and it matches the security issue that consumes it) so you're not renaming mid-stream.
- Backfill: Neither issue requires a batch backfill — "fill on login" covers existing users as they return. But note the gap: between shipping #71 and a user's next login, a record with a null DID can't be authorized by DID. Confirm the controllers fall back gracefully (or force a fill) rather than locking out not-yet-migrated users. Worth deciding the fallback behavior explicitly in step 2.

One nudge from the notes doc that's worth keeping in view: for Lucid Verify this pattern should be DID-native from day one — Verify doesn't need wallet addresses at all, so it should never inherit the header-auth pattern. Whatever DID-lookup helper you build in #71 is the thing Verify adopts directly.
